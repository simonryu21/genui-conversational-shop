GENUI · GENERATIVE UI · FLUTTER × CLAUDE

Conversation builds the screen
— a conversational shopping demo with GenUI

The LLM looks at the user's question and decides for itself which UI to draw; the Flutter app renders that spec as native widgets in real time. No screen is coded in advance — a different screen is assembled every time, driven by what the database query returned.

Today we show "generative UI" as a working demo. Ten minutes of talk, five minutes of live demo. One keyword to remember: "the UI is not pre-built — the model assembles it during the conversation."
01 · WHY
The chatbot ceiling — the answer is right, but there is no screenAn agent that only returns text vs. an agent that builds the fitting UI "together with" the answer
01

AS-IS Text chatbot

  • Recommends 3 products → a long paragraph; the user compares prices in their head
  • To "add to cart" you type again or move to another screen
  • Narrowing conditions takes several rounds of Q&A
  • Developers must pre-design every response screen → screens grow with the number of scenarios

TO-BE Generative UI (GenUI) agent

  • Recommendation → card grid; comparison → table; too many candidates → a form; a simple lookup → text only
  • A button click on a card becomes the next conversation turn (UI events are first-class citizens of the dialogue)
  • Developers define only the "available parts" (the catalog); the model does the assembly
  • The app controls the design system and the safety envelope — the model may only use permitted parts

The key question: "If every question needs a different screen, who should build that screen?" — GenUI's answer: "the model, using only the parts the app allows."

Left is the chatbot we all know. Right is what we show today. Two points: ① the model chooses the response shape ② a button click becomes the next turn. From a development standpoint the headline is "instead of N screens we built 4 parts."

① A2UI protocol

The contract between agent and app. Three forward messages — createSurface → updateComponents → updateDataModel — and one reverse message, action. It is not a model feature but a pure prompt specification, so any LLM can use it.

② Catalog

The parts dictionary the app grants the model. Built-ins (Text, Column, Button, ChoicePicker…) plus domain-specific custom parts (ProductGrid etc.). Each part's JSON Schema is both the validation rule and the prompt.

③ Surface

One chunk of UI the model created. It can be placed anywhere in the chat timeline as a Surface widget, and each surface owns a data model for form-value binding and partial updates.

This picture is the whole story. Left to right: the model "speaks" JSON, the SDK turns it into widgets. Bottom arrow: what happens in the widgets goes back to the model as JSON. Hold on to the three terms — A2UI, catalog, surface — and every later slide is just detail on those three.

  • Screen code is frozen — rendering pipeline and catalog are identical across scenarios

  "timestamp":"2026-10-14T13:50:17.870",
  "context":{"productIds":["sleeping_bag_a"]}}}

The backend forwards this JSON to the model as a user message prefixed with [UI_ACTION] {…}. The model reads action.name and context and decides whether to call add_to_cart — there is no "if addToCart then cart" branch anywhere in the FE or BE.

What this spec really is

  • A prompt specification, not a model feature. Neither Claude nor Gemini "knows" A2UI; the system prompt teaches the format, schema and rules.
  • Hence swap the LLM and the app stays the same — any agent that emits the same stream format plugs in.
  • Mixing text and JSON in one stream is deliberate — text fences instead of tool use, so that "UI appears mid-explanation."
  • Schema compliance is only an instruction; the last line of defense is client-side validation. Violations are refused at render time.
Left is the model's output; top right is how a user's click goes back to the model. A frequent question — "does Claude support A2UI?" — no, it is prompt engineering. That is why the FE stays the same when you swap the LLM.

// 1) create engine, parser, agent
surfaceController = SurfaceController(catalogs: [shopCatalog]);
_transport = A2uiTransportAdapter();
_agent = createAgent(emitChunk: _transport.addChunk); // SSE → parser

// 2) parser output → engine / chat bubble
_transport.incomingMessages.listen(surfaceController.handleMessage);
_transport.incomingText.listen(_appendAgentText);

// 3) engine output → timeline / agent
surfaceController.surfaceUpdates.listen(_onSurfaceUpdate); // surface → timeline
surfaceController.onSubmit.listen(_onUiSubmit);            // click → agent

Why this structure matters

  • Streaming safety — the LLM emits JSON token by token. The parser buffers until a fence closes or braces balance, and on parse failure returns the fragment as text so the screen never breaks.
  • Text and UI separated — from one stream, text goes to bubbles and JSON to surfaces. The order bubble → surface → new bubble is preserved naturally.
  • Validation on the client — if the model violates the schema, handleMessage rejects it. The app holds the trust boundary.
  • One swap point for the agent — match the single emitChunk callback and any LLM or server plugs in. This is why UI code is fully decoupled from the agent implementation.
A slide for the developers. What the SDK does is "parse – validate – render", and the app-side wiring is the code on the left, nothing more. Emphasize: the parser waits for incomplete JSON, and validation lives on the client.
08 · CATALOG
The catalog — the parts the model may useThe only thing developers build: name + JSON Schema + widget builder. The schema doubles as the model's spec
08
shop_catalog.dart — ProductGrid definition (abridged)
final productGridItem = CatalogItem(
  name: 'ProductGrid',
  dataSchema: S.object(properties: {          // ← validation + prompt spec
    'title': S.string(),
    'products': S.list(items: S.object(properties: {
      'productId': S.string(), 'name': S.string(),
      'price': S.integer(), 'reason': S.string(description: 'why recommended'),
    }, required: ['productId','name','price'])),
    'showTotal': S.boolean(), 'addAllLabel': S.string(),
  }, required: ['products']),
  widgetBuilder: (itemContext) {              // ← ordinary Flutter widgets
    final data = itemContext.data;
    return _GenUiFrame(child: Wrap(children: [
      for (final p in data['products']) _ProductCard(data: p,
        onAdd: () => itemContext.dispatchEvent(UserActionEvent(
          name: 'addToCart', context: {'productIds': [p['productId']]})))
    ]));
  },
);
// put the 4 custom items on top of the basic catalog → one catalog
final shopCatalog = BasicCatalogItems.asCatalog()
  .copyWith(catalogId: 'com.example.welfare-shop',
            newItems: [productGridItem, comparisonTableItem,
                       cartSummaryItem, orderConfirmationItem]);

Design points

  • Safety: components outside the catalog cannot be used; schema violations are refused at render
  • Design-system control: shape, color and spacing are Flutter code; the model fills in "content" only
  • Event design: custom parts have fixed action names (addToCart); standard Buttons get actions the model defines on the spot
The answer to "so what do developers do?" We built four parts, each a schema plus a widget builder. The charm of GenUI is that the schema doubles as the manual handed to the model. We own the design, the model owns the content.

System prompt — the UI component spec section (a summary of the catalog schema)
# Available components (catalogId: com.example.welfare-shop)
- ProductGrid — grid of recommended product cards
  props: title?, products[{productId*, name*, price*(int), reason?}], showTotal?, addAllLabel?
  built-in action: Add → addToCart {productIds:[id]}
- ComparisonTable — props: title?, products[…], rows[{label*, values*[]}], recommendation?
- CartSummary — props: items[…], total*, balanceAfter*, note?
- OrderConfirmation — props: orderId*, total*, status*, …
## Standard components
- Column: {children:[id,…]}   - Text: {text}
- Button: {child, variant, action:{event:{name, context:{key:{"path":"/path"}}}}}
- ChoicePicker: {label, displayStyle:"chips", options:[…], value:{"path":"/path"}}

Design points

  • Short and cache-friendly — easy to tune together with the domain rules (tools, purchase flow, judgment guidance) as one block
  • Good enough — in measurement the model never violated the schema
  • The server holds the keys — LLM calls, API keys and tool execution stay in the backend
  • Trade-off — the contract lives in two places (catalog and prompt), and only the standard parts listed in the spec can be used. Generating it from the catalog with the SDK's PromptBuilder is the alternative. The FE validation is the final guard
The answer to "what do you give the LLM?" Not just the question — three chunks. The code in the middle is the point: the Flutter catalog schema transcribed into human-readable sentences. Hence the trade-off of maintaining two places. Mention PromptBuilder as the alternative and move on.
