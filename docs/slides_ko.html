GENUI · GENERATIVE UI · FLUTTER × CLAUDE

말만 하면 UI가 만들어진다
— GenUI 쇼핑 어시스턴트 데모

사용자의 질문을 보고 LLM이 어떤 UI를 그릴지 스스로 결정하고, Flutter 앱은 그 명세를 네이티브 위젯으로 실시간 렌더링합니다. 화면마다 Flutter 코드를 미리 짜 두지 않아도, DB 조회 결과에 따라 매번 다른 화면이 조립됩니다.

오늘은 "생성형 UI"라는 개념을 실제 돌아가는 데모로 보여드립니다. 10분 발표 후 라이브 데모 5분. 키워드 하나만 기억해 주시면 됩니다 — "UI를 미리 만들어 두는 게 아니라, 대화 중에 모델이 조립한다."
01 · WHY
챗봇의 한계 — 답은 맞는데 화면이 없다텍스트만 돌려주는 에이전트 vs. 상황에 맞는 UI를 "함께" 만드는 에이전트
01

AS-IS 텍스트 챗봇

  • 상품 3개 추천 → 긴 문단으로 나열, 가격 비교는 사용자가 머릿속에서
  • "담기"를 하려면 다시 타이핑하거나 다른 화면으로 이동
  • 조건을 좁히려면 질문-답변을 여러 번 반복
  • 개발자가 모든 응답 화면을 미리 설계해야 함 → 시나리오 수만큼 화면 수가 늘어남

TO-BE 생성형 UI(GenUI) 에이전트

  • 추천이면 카드 그리드, 비교면 비교표, 후보가 많으면 선택 폼, 단순 조회면 텍스트만
  • 카드의 버튼 클릭이 곧바로 다음 대화 턴이 됨 (UI 이벤트가 대화의 일급 시민)
  • 개발자는 "쓸 수 있는 부품(카탈로그)"만 정의, 조립은 모델이
  • 디자인 시스템·안전 범위는 앱이 통제 — 모델은 허용된 부품만 사용 가능

핵심 질문: "질문마다 다른 화면이 필요하다면, 그 화면을 누가 만들어야 하는가?" — GenUI의 답은 "모델이, 단 앱이 허용한 부품으로."

GenUI 데모 · 01 WHY
왼쪽은 우리가 익숙한 챗봇. 오른쪽이 오늘 보여드릴 것. 포인트는 두 가지: ① 응답 형태를 모델이 고른다 ② 버튼 클릭이 다음 턴이 된다. 개발 관점에선 "화면을 N개 만드는 대신 부품 4개를 만들었다"가 핵심.

① A2UI 프로토콜

에이전트와 앱 사이의 계약. createSurface → updateComponents → updateDataModel 3종 메시지와 역방향 action 1종. 모델 차원 기능이 아니라 순수 프롬프트 규격이라 어떤 LLM이든 쓸 수 있습니다.

② 카탈로그 (Catalog)

앱이 모델에게 허용하는 부품 사전. 기본 제공(Text, Column, Button, ChoicePicker…) + 도메인 커스텀(ProductGrid 등). 각 부품의 JSON Schema가 검증 규칙이자 프롬프트가 됩니다.

③ 서피스 (Surface)

모델이 만든 UI 한 덩어리. 채팅 타임라인 어디든 Surface 위젯으로 끼워 넣을 수 있고, 서피스마다 데이터 모델을 가져 폼 값 바인딩·부분 갱신이 가능합니다.

GenUI 데모 · 02 CONCEPT
그림 한 장이 전부입니다. 왼→오: 모델이 JSON을 "말하면" SDK가 위젯으로 바꾼다. 아래 화살표: 위젯에서 일어난 일이 JSON으로 모델에게 돌아간다. 세 용어(A2UI, 카탈로그, 서피스)만 잡고 가시면 이후 슬라이드가 전부 이 셋의 세부입니다.

검증 설계 원칙

  • 화면 코드는 고정 — 렌더링 파이프라인·카탈로그는 시나리오와 무관하게 동일
  • BE → FE 스트림은 단일 계약: 마크다운 + ```json A2UI 블록 + ▸ tool trace 라인
  • tool trace는 실제 tool_use 이벤트에서 생성 — 모델이 지어내지 않음
  • UI 액션(담기·결제)도 하드코딩 라우팅 없이 모델이 판단해 도구 호출
  • 모든 턴은 JSONL 로그로 증적 (도구 인자·토큰·지연시간)

동적성 = 화면을 미리 만들어 두는 것이 아니라, 질문과 DB 조회 결과를 보고 모델이 그때그때 UI를 조립하는 성질. 검증 목표는 "같은 Flutter 코드로도 질문마다 화면이 달라지는가". 상품 데이터: Open Food Facts 한국 식품 226종 + 데모 시드 91종

  "context":{"productIds":["sleeping_bag_a"]}}}

BE는 이 JSON을 [UI_ACTION] {…} 접두어를 붙인 user 메시지로 모델에게 전달합니다. 모델은 action.name과 context를 읽고 add_to_cart를 호출할지 판단합니다 — FE·BE 어디에도 "addToCart면 장바구니" 같은 분기 코드가 없습니다.

이 규격의 정체

  • 모델 기능이 아니라 프롬프트 규격입니다. Claude·Gemini 어느 쪽도 A2UI를 "알지" 못하며, 시스템 프롬프트가 형식·스키마·규칙을 가르칩니다.
  • 그래서 LLM을 바꿔도 앱은 그대로 — 같은 형식의 스트림만 내면 어떤 에이전트든 연결됩니다.
  • 텍스트와 JSON이 한 스트림에 섞이는 것이 의도된 설계 — "설명하다가 중간에 UI가 나타나는" UX를 위해 tool use 대신 텍스트 펜스를 씁니다.
  • 스키마 준수는 지시일 뿐, 최종 방어선은 클라이언트 검증. 위반하면 렌더링이 거부됩니다.

왜 이 구조가 중요한가

  • 스트리밍 안전성 — LLM은 JSON을 토큰 단위로 끊어 보냅니다. 파서는 펜스가 닫히거나 중괄호가 균형을 이룰 때까지 버퍼링하고, 파싱 실패 시 그 조각을 텍스트로 돌려보내 화면이 깨지지 않게 합니다.
  • 텍스트와 UI의 분리 — 같은 스트림에서 텍스트는 말풍선으로, JSON은 서피스로 갈라집니다. 말풍선 → 서피스 → 새 말풍선 순서가 자연스럽게 유지됩니다.
  • 검증은 클라이언트에서 — 모델이 스키마를 어기면 handleMessage 단계에서 거부. 앱이 신뢰 경계를 쥡니다.
  • 에이전트 교체 지점이 하나 — emitChunk 콜백 하나만 맞추면 어떤 LLM·서버든 연결됩니다. UI 코드가 에이전트 구현과 완전히 분리되는 이유.

- Column: {children:[id,…]}   - Text: {text}

- ChoicePicker: {label, displayStyle:"chips", options:[…], value:{"path":"/경로"}}

설계 포인트

  • 짧고 캐시 친화적 — 도메인 규칙(도구·구매 흐름·판단 지침)과 한 덩어리로 다듬기 쉽다
